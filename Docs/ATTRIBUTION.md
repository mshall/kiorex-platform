# Attribution core services (GRW-P1-B)

Plan: `kiorex-v2/_docs/growth/` (ARCH section 6, 8 and 16; work-packages package B). Contract: `@kiorex/contracts` 1.10.0. Every default is `PROPOSED_DEFAULT` until the founder ratifies it. Flag `growth.attribution` OFF = no decision is made and bookings stay UNATTRIBUTED, exactly as before the engine existed.

## The decision function
`src/growth/attribution/decide.ts` is PURE (no I/O, no clock, no randomness). Rules in order: (1) channel `CLINIC_LINK` or a verified `lt` token for the same organisation: `PROVIDER_LED / EXPLICIT_PROVIDER_CHANNEL`; (2) a provider-owned touch for the same organisation inside `providerTouchWindowDays` (30) whose landing was actually rendered (`dwellMs >= minDwellMsForProviderTouch`, 1000): `PROVIDER_FIRST` (default) means any such touch wins, `LAST_NON_DIRECT` only when the latest non-direct touch is the provider's; (3) a patient-referral touch inside `patientReferralWindowDays` (30): `MARKETPLACE / PATIENT_REFERRAL`; (4) any marketplace touch (campaign click inside `campaignClickWindowDays` 7, search, direct, WhatsApp): `MARKETPLACE / MARKETPLACE_TOUCH`; (5) else `UNATTRIBUTED / NO_PROVIDER_EVIDENCE`. Window edges are inclusive (30 d is in, 30 d 1 s is out); only touches strictly before the booking count; another organisation's touch is ignored; ties pick the latest touch, then the smallest id. `FIRST_TOUCH` is reporting only and the function refuses it (the policy resolver falls back to `PROVIDER_FIRST` rather than fail a booking). It can only REMOVE a fee (PROVIDER_LED): MARKETPLACE and UNATTRIBUTED are both what the Clinic charges today.

## Decision record
`AttributionService.decideForBooking({bookingId, visitorKey?, ltToken?})` loads the facts, calls `decide`, and writes ONE immutable `GrowthAttributionDecision` per (booking, policy version) in one transaction with the `BookingIntent` pointer (`acquisitionOrigin`, `attributionDecisionId`) and the internal event `AttributionAssigned` (and `PatientAcquisitionRecorded` once per subject). The row stores the policy version id, `inputsHash` (the contracts helper `computeAttributionInputsHash`), the reason code, every touch considered (`evidenceTouchIds`, the replayable evidence), the winning touch and a booking snapshot with the policy payload as it was. `replay(decisionId)` re-runs the pure function on the stored inputs and must reproduce the stored result (SLI 100 %). The policy cited is the one active AT the booking's creation time, so an old booking is always explained by the policy that applied then. `acquisitionBlock(bookingId)` builds the additive `acquisition` block for `POST /marketplace/v1/bookings` (package C attaches it).

Overrides: `correct(actor, bookingId, {origin, note})` needs `super_admin`, a note of at least 10 characters, appends a NEW decision (`supersedesId`, `actor`, `note`, reason `MANUAL_CORRECTION`) and writes `AuditLog growth.attribution.correct`; a PROVIDER_LED decision can never be turned into a chargeable origin (`403 CORRECTION_CANNOT_ADD_FEE`: evidence only removes a fee).

## Public endpoints (`/api/v1`, rate limited per rotating ipHash through the shared Postgres limiter)
`POST /growth/v1/touch` (202; body cap 4 KiB; unknown keys dropped; an e-mail-like or PHI-like UTM value rejects the whole call; a bad or expired `lt` is 400; with no `X-KX-Consent: analytics` or the `growth.analytics_visitor` gate unsatisfied NOTHING is stored and no cookie is set), `POST /growth/v1/events` (batch of 1 to 20 canonical client names, `careType` allowed, specialty, provider ids and PHI-like values rejected, idempotent, nothing of a rejected batch is stored), `GET /growth/v1/evidence/:bookingId` (ops session, or a signed Clinic request with `X-Kiorly-Org-Ref`; facts only, never visitor keys or ip hashes), `GET /growth/config/resolve?kind=&market=` (ops). Errors use `GROWTH_ERROR_CODES` from the contract.

## Configuration (GrowthConfigService)
Versioned `GrowthConfigVersion`: `DRAFT -> PENDING_APPROVAL -> APPROVED -> ACTIVE -> SUPERSEDED | ROLLED_BACK`, maker-checker (approver is a super admin and not the author; also a database CHECK), effective dates (an APPROVED version activates when its date arrives, the previous ACTIVE row is closed at that instant), `ATTRIBUTION_POLICY` needs an announcement and `effectiveFrom >= approval + 7 days`, rollback = a NEW version copying an older payload with its own approval, every transition in `AuditLog growth.config.<transition>` (checksums only). Resolution: MARKET scope, then GLOBAL, then the `PROPOSED_DEFAULT` payloads (materialised once as an ACTIVE row `ticket=PROPOSED_DEFAULT` so decisions can cite a version id). Controllers for create, approve and rollback belong to package K.

## Funnel events, slugs, retention, erasure, fraud
`GrowthEvent.dedupeKey` (unique) makes ingestion idempotent: client events key on identity (visitor key with consent, else the rotating ip hash) + name + landing + careType + props + minute; server facts (`GrowthEventsService.recordFact`) key on `fact|name|naturalKey`, so the same fact reported by web, mobile, messaging and backend is stored once. `SlugService` keeps `GrowthSlug` + `GrowthSlugHistory` (old slugs answer 301 to the current one, never reused by another entity). `RetentionJob` (every 6 h) calls `GrowthMaintenanceService.purgeExpired` with the months from the active policy. `SubjectDeletedConsumer` registers the `growth` anonymiser on `PatientService`, so `subject.deleted` (and in-app deletion) calls `GrowthMaintenanceService.eraseSubject`: touches a decision considered are anonymised (identifiers nulled, kept as evidence), the rest deleted. Fraud hooks (`CLICK_WITHOUT_RENDER`, `BURST_PER_IP_HASH`, `PROVIDER_LED_SHARE_JUMP`) write `GrowthFraudSignal` rows with keyed hashes only and never change a decision.

## Known limits
The Clinic signs the evidence request with one shared secret, so `X-Kiorly-Org-Ref` is a claim by an authenticated Clinic, not a per-organisation proof (per-organisation partner credentials are a follow-up). The link code to organisation mapping (`GrowthAcquisitionSource.ownerOrgRef`) is learned from a Clinic-signed `lt` or the `ReferralLinkCreated` event (`LinkRegistryService`, GRW-P1-C); a code belongs to one organisation and a conflicting claim is refused. Both token formats are verified (the Clinic's `kx-lt1` provider-link token with the shared Clinic secret, and the `kxl1.` in-session token with `GROWTH_LINK_TOKEN_SECRET`). A revoked link: Kiorex does not see revocations, so a still-valid signed token (72 h) keeps deciding PROVIDER_LED; evidence only removes a fee, never adds one.
